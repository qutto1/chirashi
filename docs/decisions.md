## 2026-07-15: Webアプリ「LINEへ送信」の中継方式

**背景**: Webアプリ（公開GitHub Pages）の「LINEへ送信」を、毎朝の通知先（ボット→登録2ユーザーへのプッシュ）と同じ宛先へ直接送るには、LINEチャネルトークンを使うプッシュ送信が必要。トークンは公開ページに置けないため中継サーバーが要る。

**提示した選択肢**:
1. **GAS中継（推奨・採用）** — Google Apps Scriptを無料の中継サーバーにする。ユーザーのGoogleアカウントで常時稼働、トークンはScript Propertiesに安全保管。初回のみコードを貼り付けてデプロイし、URLを設定。PCの電源状態に依存しない。
2. PC+トンネル中継 — PCで小さな中継サーバー＋常設Cloudflareトンネル。既存トークンを流用できるがPC起動・トンネル維持が前提。
3. 共有ピッカーのまま — 現状の `line.me/R/share`（送信時に宛先を選ぶ）を維持。中継サーバー不要。

**選択**: 1. GAS中継

**実装方針**:
- GASスクリプト（`gas/line-relay.gs`）: doPostで `{secret, text}` を受け、Script Properties のトークン・user_ids でLINE multicastプッシュ。共有シークレットで簡易保護。宛先はサーバー側固定なので、万一エンドポイントが漏れても送信先は本人のLINEのみ。
- Webアプリ: 設定画面にGAS URL・シークレットを入力（localStorageに端末ローカル保存、公開ソースには含めない）。未設定時は従来の共有ピッカーにフォールバック。

## 2026-08-26: 低解像度チラシ画像はGeminiに渡さない（捏造の入口を塞ぐ）

**背景**: 8/26朝の通知で、ラ・ムー高岡東店に存在しない「かつおしょうゆ 1L 148円」が載り、常時チェック商品「しょうゆ」が誤って「あり」と通知された。原因は、ラ・ムーのチラシ本体（`DA_20260826_31.pdf` / `.jpg`）が404で、フォールバックの `...B.jpg`（**255×180のサムネイル**）だけが取得でき、それをGeminiに渡したこと。判読不能な画像でもGeminiは応答を返すため、それらしい商品を捏造する。実物のB面にあったのは「ヤマサ醤油 そうめん専科 500ml 148円」で、価格だけが偶然一致していた。

**検討した代替案**:
1. **入口で低解像度画像を弾く（採用）** — 幅700px/高さ500px未満は解析対象から除外。全滅した店は商品0件とし、自己テストで要確認として報告する。捏造を構造的に防げる。
2. プロンプトで「読めなければ空配列を返せ」と指示するだけ — LLMの自己申告に依存し、今回のように自信を持って捏造されると効かない。
3. 取得URLの網羅だけ強化する — 今回は直せるが、将来サムネイルしか無い日に同じ捏造が再発する。

**決定**: 1を採用（2の指示も既存プロンプトに残す）。加えて取得側も強化：
- ラ・ムーのPDF候補を `base.pdf` / `baseA.pdf` / `baseB.pdf` の3通り試し、見つかった面をすべて使う（8/26はA面・B面の2枚組で公開されていた）。
- `git push` がリモート先行で拒否されたら `pull --rebase` して1度だけ再試行（アプリからの `settings.json` 保存とぶつかり、8/26朝は公開が丸ごと失敗していた）。

**帰結**: 再解析でラ・ムーは1667×1178の高解像度2面から14商品を正しく抽出し、「かつおしょうゆ」は消えた。「しょうゆ」の判定も `なし` に是正。回帰テストを `test_selftest.py` に追加（`filter_low_res` / `_lamu_pdf_candidates` / 低解像度時の自己テスト）。

**残課題**: 掲載判定は単純な部分一致のため、「しょうゆ」は「醤油」（漢字）にヒットしない。表記ゆれ対応は未着手。
