# 意思決定ログ

## 2026-07-15: Webアプリ「LINEへ送信」の中継方式

**背景**: Webアプリ（公開GitHub Pages）の「LINEへ送信」を、毎朝の通知先（ボット→登録2ユーザーへのプッシュ）と同じ宛先へ直接送るには、LINEチャネルトークンを使うプッシュ送信が必要。トークンは公開ページに置けないため中継サーバーが要る。

**提示した選択肢**:
1. **GAS中継（推奨・採用）** — Google Apps Scriptを無料の中継サーバーにする。ユーザーのGoogleアカウントで常時稼働、トークンはScript Propertiesに安全保管。初回のみコードを貼り付けてデプロイし、URLを設定。PCの電源状態に依存しない。
2. PC+トンネル中継 — PCで小さな中継サーバー＋常設Cloudflareトンネル。既存トークンを流用できるがPC起動・トンネル維持が前提。
3. 共有ピッカーのまま — 現状の `line.me/R/share`（送信時に宛先を選ぶ）を維持。中継サーバー不要。

**選択**: 1. GAS中継

**実装方針**:
- GASスクリプト（`gas/line-relay.gs`）: doPostで `{secret, text}` を受け、Script Properties のトークン・user_ids でLINE multicastプッシュ。共有シークレットで簡易保護。宛先はサーバー側固定なので、万一エンドポイントが漏れても送信先は本人のLINEのみ。
- Webアプリ: 設定画面にGAS URL・シークレットを入力（localStorageに端末ローカル保存、公開ソースには含めない）。未設定時は従来の共有ピッカーにフォールバック。

## 2026-08-26: 低解像度チラシ画像はGeminiに渡さない（捏造の入口を塞ぐ）

**背景**: 8/26朝の通知で、ラ・ムー高岡東店に存在しない「かつおしょうゆ 1L 148円」が載り、常時チェック商品「しょうゆ」が誤って「あり」と通知された。原因は、ラ・ムーのチラシ本体（`DA_20260826_31.pdf` / `.jpg`）が404で、フォールバックの `...B.jpg`（**255×180のサムネイル**）だけが取得でき、それをGeminiに渡したこと。判読不能な画像でもGeminiは応答を返すため、それらしい商品を捏造する。実物のB面にあったのは「ヤマサ醤油 そうめん専科 500ml 148円」で、価格だけが偶然一致していた。

**検討した代替案**:
1. **入口で低解像度画像を弾く（採用）** — 幅700px/高さ500px未満は解析対象から除外。全滅した店は商品0件とし、自己テストで要確認として報告する。捏造を構造的に防げる。
2. プロンプトで「読めなければ空配列を返せ」と指示するだけ — LLMの自己申告に依存し、今回のように自信を持って捏造されると効かない。
3. 取得URLの網羅だけ強化する — 今回は直せるが、将来サムネイルしか無い日に同じ捏造が再発する。

**決定**: 1を採用（2の指示も既存プロンプトに残す）。加えて取得側も強化：
- ラ・ムーのPDF候補を `base.pdf` / `baseA.pdf` / `baseB.pdf` の3通り試し、見つかった面をすべて使う（8/26はA面・B面の2枚組で公開されていた）。
- `git push` がリモート先行で拒否されたら `pull --rebase` して1度だけ再試行（アプリからの `settings.json` 保存とぶつかり、8/26朝は公開が丸ごと失敗していた）。

**帰結**: 再解析でラ・ムーは1667×1178の高解像度2面から14商品を正しく抽出し、「かつおしょうゆ」は消えた。「しょうゆ」の判定も `なし` に是正。回帰テストを `test_selftest.py` に追加（`filter_low_res` / `_lamu_pdf_candidates` / 低解像度時の自己テスト）。

**残課題**: 掲載判定は単純な部分一致のため、「しょうゆ」は「醤油」（漢字）にヒットしない。表記ゆれ対応は未着手。

**出典**: `notify.py` の `filter_low_res` / `_lamu_pdf_candidates` / `git_push`、`notify.log` 2026-08-26 08:00:09 の404ログ。


## 2026-09-29: 設定はGitHubへ自動同期し、Geminiは代替モデルへ切替、失敗はLINE/アプリに明示する

**背景**: 同日、2件の不具合が報告された。
1. 大阪屋の情報が全く取得できなかった。ログでは主モデル `gemini-3-flash-preview`（プレビュー版）が 503（高負荷）を5回返し、再試行の合計待機75秒で全滅していた。あわせて「サンコーも0件」だったが、こちらは故障ではなく、サンコーのPDF自体が「本日チラシの掲載はございません」の告知ページで、0件が正しかった。
2. スマホで直した「常時チェックする商品」が今朝のLINEに反映されていなかった。GitHubの `settings.json` に反映されたのは同日 16:39 で、朝のジョブ（08:00）より後だった。原因は前回の変更（8/25）自体にあった。「追加・削除は端末(localStorage)へ即保存、GitHubへは『保存』ボタンを押した時だけ送る」設計のため、画面には反映済みに見えるのにLINEが読むGitHub側は古いまま、という食い違いを作っていた。

**検討した代替案と決定**:

*設定の同期*
1. **編集のたびに自動でGitHubへ反映＋反映状態を常時表示（採用）** — 追加・削除・時刻変更を約0.8秒のデバウンスで自動PUT。設定画面に「✅反映済み／⏳反映中／⚠この端末だけ」を出し、⚙に未反映の印を付ける。
2. 「保存」ボタンを目立たせるだけ — 押し忘れが再発するため不採用。
3. 端末ローカルへの退避をやめる — PAT未設定の端末で編集が消える問題が戻るため不採用。

　付随して、端末が「最後に同期した内容(base)」を持つようにした。未反映の編集がある端末はローカル優先、無ければGitHub側を採用する。これにより、古い端末の内容が別端末の新しい設定を上書きしない。バックエンドの設定読み込みは、最大5分キャッシュされる raw.githubusercontent.com ではなく Contents API を優先し、読み込んだ設定をログに残す。

*Gemini障害*
1. **主モデル→代替モデル（`gemini-flash-latest`, `gemini-2.5-flash`）へ切替＋失敗店を3分おいて最大2回再試行（採用）**
2. 主モデルの再試行時間を延ばすだけ — 高負荷が長引く日に他店の処理まで遅れるため不採用。
3. 失敗した店は前日データで埋める — 期間・価格が古いまま「今日の特売」に見える誤情報になる（8/25に日付ずれを問題視済み）ため不採用。

*失敗の見せ方*
　店舗に `status`（ok / failed / no_flyer）を持たせる。LINEには「⚠取得できませんでした」「ℹ本日チラシの掲載なし」を表示し、取得失敗の店がある日の「なし」には「（大阪屋は未確認）」を添える（「しょうゆ：なし」と断定すると誤情報になるため）。アプリの店舗カードにも理由を表示する。自己テストは、解析失敗だけを要確認とし、正常な0件（掲載なし告知）は誤警報にしない。

**帰結**: 今日の大阪屋は再取得して29商品を反映済み。回帰テストを `test_selftest.py` に追加（モデル切替・再試行・status・LINE本文・設定URL）。アプリの同期は実ブラウザで検証し、その過程で `App.settings` と `App.remote` が同一オブジェクトを共有して常に「反映済み」と誤判定するバグを見つけて修正した。手動リカバリ用に `tokubai-notifier/regen_store.py` を追加。

**残課題**: 同じ日に別端末が古い状態から編集した場合は、最後に反映した端末が勝つ（マージはしない）。掲載判定が単純な部分一致のため「しょうゆ」は「醤油」にヒットしない（8/26から継続）。

**出典**: `notify.log` 2026-09-29 08:01〜08:04（503×5）、`settings.json` のコミット履歴（16:39）、`js/app.js` の設定同期処理。
